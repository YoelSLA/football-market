== Catálogo de jugadores

Ambos endpoints requieren un JWT Bearer válido. La sincronización está disponible
para cualquier usuario autenticado, sin rol adicional. No se ejecuta automáticamente.

=== Consulta paginada

`GET /api/players` consulta exclusivamente la base local. `page` comienza en cero;
`size` admite valores de 1 a 100. Los valores predeterminados son 0 y 20.

El `id` es interno de FootballMarket. Cada jugador contiene además `name`, `team`,
`league`, `position`, `dateOfBirth`, `nationality`, `imageUrl` y `fallbackImageUrl`.
Los cuatro últimos aparecen como `null` cuando son desconocidos. No se exponen referencias externas
ni el estado activo. La migración V3 reasigna los IDs anteriores y conserva el
identificador de Football-Data.org exclusivamente en su referencia externa.

=== Sincronización manual

`POST /api/players/sync` no recibe body. Primero obtiene Premier League (`PL`),
Bundesliga (`BL1`), La Liga (`PD`), Serie A (`SA`) y Ligue 1 (`FL1`), sin exigir un orden,
y después aplica la foto completa dentro de una transacción. Si falla cualquiera
de las cinco ligas, el catálogo permanece sin cambios. La configuración debe ser
el conjunto `PL,BL1,PD,SA,FL1` en cualquier orden; una lista incompleta, con duplicados o ligas adicionales impide el arranque.
Los jugadores ausentes se conservan como inactivos.

La resolución usa `(FOOTBALL_DATA, externalId)`; una alta crea conjuntamente el jugador
y su referencia. Los datos opcionales ausentes o inválidos no borran valores conocidos.
La sincronización no obtiene ni modifica imágenes ni consulta otros proveedores.
Ante `429` se respeta `Retry-After` con un máximo de tres reintentos por petición;
otros errores HTTP o de comunicación no se reintentan.

Un conflicto de referencia identificado se descarta sin reasignar jugadores. Si se
detecta durante la persistencia, se revierte el intento y se reaplica la misma foto
en una transacción nueva, sin repetir HTTP. Solo se publican contadores del commit
final. Otros errores técnicos revierten la aplicación local sin cambios parciales.

== Imágenes de jugadores

Todos los endpoints requieren JWT Bearer válido. La sincronización es manual y
síncrona; no se invoca al proveedor durante las consultas de auditoría. `force`
es `false` por defecto. Las URLs válidas anteriores permanecen si el proveedor
no ofrece una sustitución. Los resultados individuales se consultan por separado.

=== Sincronización manual de imágenes

`POST /api/players/images/sync` admite `force=true` sin body. Un resultado parcial
también responde `200`; una ejecución concurrente responde `409` sin crear otro run.
Ante un fallo global se conservan los resultados previamente confirmados.

=== Historial de sincronizaciones

`GET /api/players/images/sync-runs` devuelve resúmenes por inicio e ID
descendentes. `page` comienza en 0 (valor por defecto 0), `size` admite
1–100 (por defecto 20). La retención configurable elimina runs expirados y sus
items, sin borrar referencias, resoluciones ni imágenes.

=== Detalle paginado de un run

`GET /api/players/images/sync-runs/{id}/items` devuelve el resultado de cada
jugador en orden ascendente de item. Usa los mismos límites de paginación.
`INTERRUPTED` preserva el último estado durable de resolución y no suma a
`failed`; la recuperación de runs huérfanos ocurre al arrancar.

== Autenticación

=== Usuario actual

`GET /api/auth/me` requiere un JWT Bearer válido cuyo sujeto identifique a un
usuario existente. Devuelve exclusivamente el `id` y el `email` actuales obtenidos
de persistencia. No recibe body ni parámetros.
